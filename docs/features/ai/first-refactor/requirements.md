# Requirements: AI-First Architecture Refactoring

## Overview

基于 `ai-first-gap-analysis` 和 `project-cognition-reanalysis` 的分析结论，本项目旨在对 Knowledge Radar 系统进行深度的架构与交互重构。核心目标是将 AI 从可选的辅助工具提升为系统的核心认知引擎，确保所有涉及信息加工的操作都必须经过 AI 处理，并建立"AI 建议 - 人类确认"的人机协作模式。

**核心体验原则：AI 强感知 (AI Perception)**
用户必须清晰地感知到 AI 的存在和工作过程。系统不仅要展示 AI 的"结果"，还要展示 AI 的"思考过程"和"依据"。
- **显性化**：AI 的处理不再是后台静默任务，而是前台可见的交互流程。
- **可解释**：AI 必须解释"为什么"（Reasoning），而不仅仅是给结果。
- **实时性**：用户操作后立即触发 AI 反馈，拒绝无响应的异步等待。

## User Stories

### Story 1: AI 辅助创建金字塔 (Create with AI)

As a 知识整理者, I want 在创建金字塔时通过自然语言描述获得 AI 生成的结构建议, so that 我可以快速构建高质量的知识框架，减少手动操作。

**Acceptance Criteria:**

- [ ] AC1: 描述生成建议（正常场景）
  - **Given**: 用户输入金字塔名称和一段关于金字塔主题的详细描述
  - **When**: 用户点击"生成建议"按钮
  - **Then**:
    - 系统调用 AI 分析描述，识别核心概念和层次结构
    - **UI 展示 AI 的思考过程**（如："正在分析主题..." -> "识别到核心概念..." -> "正在构建层级..."）
    - 返回可视化树形结构建议，包含至少 3 层节点
    - **UI 展示 AI 生成理由**（Reasoning）："基于描述，我理解这是关于...，因此建议..."
    - 返回状态为 `pending_confirmation`

- [ ] AC2: 用户确认并创建
  - **Given**: 系统已生成金字塔结构建议，用户对建议进行了微调（修改节点名称或位置）
  - **When**: 用户点击"确认创建"
  - **Then**:
    - 系统保存金字塔及其完整的节点结构
    - 记录 AI 的原始建议 ID 和用户的修改历史
    - 返回创建成功的金字塔 ID

- [ ] AC3: 描述过于简略
  - **Given**: 用户输入的描述少于 10 个字
  - **When**: 用户点击"生成建议"
  - **Then**: 系统提示"描述太短，AI 难以生成有效建议，请补充更多细节"

### Story 2: 信息源智能分析 (Add Source with Analysis)

As a 知识整理者, I want 在添加信息源 URL 后立即看到 AI 的分析结果和关联建议, so that 我能确保信息源的价值并将其正确归类。

**Acceptance Criteria:**

- [ ] AC1: URL 预览与分析
  - **Given**: 用户输入一个有效的 URL
  - **When**: 用户点击"分析"按钮
  - **Then**:
    - **UI 展示 AI 抓取与分析进度**（如"抓取成功，正在分析主题..."）
    - AI 分析内容主题，生成标签和分类建议
    - **UI 展示 AI 分类理由**："本文主要讨论 X，与节点 Y 的匹配度为 0.9，建议归类到..."
    - 界面展示分析结果卡片，包含 AI 提取的关键摘要

- [ ] AC2: 确认添加信息源
  - **Given**: 界面展示了 AI 的分析结果和关联建议
  - **When**: 用户确认关联建议并点击"保存"
  - **Then**:
    - 系统保存信息源配置
    - 自动创建与指定节点的关联关系
    - 记录信息源的初始 AI 分析数据

### Story 3: 内容实时分类 (Input Content with Classification)

As a 用户, I want 在提交内容（URL/文本/文件）后立即看到 AI 的分类和处理结果, so that 我确认系统正确理解了我的输入。

**Acceptance Criteria:**

- [ ] AC1: 提交即时反馈
  - **Given**: 用户提交了一个 URL 或一段文本
  - **When**: 提交请求发送
  - **Then**:
    - **UI 展示 AI 处理状态**（如"AI 正在阅读..."）
    - AI 生成分类建议（属于哪个金字塔的哪个节点）
    - **UI 展示 AI 处理结果**：显示分类路径和置信度（Confidence）
    - 界面展示处理结果，状态显示为 `PROCESSED`（而非 `PENDING`）

- [ ] AC2: 纠正分类建议
  - **Given**: AI 建议将内容分类到"未分类"或错误的节点
  - **When**: 用户手动选择正确的节点并确认
  - **Then**:
    - 系统更新内容的分类信息
    - 系统记录用户的纠正行为，用于优化后续推荐

### Story 4: 节点变更影响分析 (Update Node with Impact Analysis)

As a 知识整理者, I want 在修改节点描述时获得 AI 的影响评估, so that 我能知道这次修改是否需要调整其子节点或关联内容。

**Acceptance Criteria:**

- [ ] AC1: 描述变更检测
  - **Given**: 用户修改了某节点的描述，且语义发生显著变化
  - **When**: 用户点击"保存"
  - **Then**:
    - 系统异步/同步调用 AI 分析新旧描述的差异
    - 如果差异影响到子节点的归属或内容的分类，系统弹出"影响评估报告"
    - 报告列出可能需要移动的子节点或内容

- [ ] AC2: 确认变更影响
  - **Given**: 系统弹出了影响评估报告
  - **When**: 用户确认报告中的建议（如移动某些子节点）
  - **Then**:
    - 系统执行节点更新
    - 系统自动执行建议的关联变更
    - 生成一条变更日志

### Story 5: 金字塔变更影响分析 (Update Pyramid with Impact Analysis)

As a 知识整理者, I want 在修改金字塔核心定义（名称/描述）时获得 AI 的重构建议, so that 整个知识体系保持一致性。

**Acceptance Criteria:**

- [ ] AC1: 金字塔重定义
  - **Given**: 用户大幅修改了金字塔的描述（定义了新的知识边界）
  - **When**: 用户保存修改
  - **Then**:
    - AI 分析现有结构与新定义的契合度
    - 如果发现大量节点不再符合新定义，生成"重构提案"

### Story 6: 搜索意图理解 (Search with Intent)

As a 用户, I want 搜索时系统能理解我的真实意图而非仅匹配关键词, so that 我能找到语义相关但用词不同的内容。

**Acceptance Criteria:**

- [ ] AC1: 语义搜索
  - **Given**: 用户输入自然语言查询（如"如何构建 Agent"）
  - **When**: 用户执行搜索
  - **Then**:
    - **UI 展示 AI 思考过程**："理解查询意图... 扩展关键词：Autonomous, LLM..."
    - 系统执行混合检索
    - 返回结果列表，每个结果**展示 AI 推荐理由**（"因匹配概念 X 而推荐"）
    - 高亮匹配的语义片段

### Story 7: 批量导入与去重 (Batch Import with Optimization)

As a 管理员, I want 在批量导入内容时自动去重并分类, so that 知识库保持整洁。

**Acceptance Criteria:**

- [ ] AC1: 批量导入预处理
  - **Given**: 用户上传包含 100 条记录的 CSV/JSON
  - **When**: 用户点击"导入"
  - **Then**:
    - 系统对每条记录进行指纹计算，识别重复项
    - AI 对新增项进行批量分类建议
    - 返回预览报告：新增 N 条，重复 M 条，建议分类情况

### Story 8: 信息源配置变更影响 (Update Source Config with Analysis)

As a 管理员, I want 在修改信息源抓取规则时知道会抓取到什么样的新内容, so that 我能优化抓取质量。

**Acceptance Criteria:**

- [ ] AC1: 规则变更预览
  - **Given**: 用户修改了信息源的 CSS 选择器或过滤规则
  - **When**: 用户点击"测试规则"
  - **Then**:
    - 系统使用新规则试抓取最近 5 条内容
    - AI 分析新抓取内容的质量和相关度
    - 展示新旧规则抓取结果的对比

## Constraints

- **响应时间**: 用户直接交互的 AI 分析（如创建金字塔建议、单条内容分类）需在 **5秒内** 返回结果（或首字节）。
- **可用性**: 若 AI 服务不可用，系统应提供降级方案（如允许手动创建但不提供建议），并明确提示用户。
- **一致性**: 所有 AI 生成的数据必须记录元数据（生成时间、模型版本、置信度），以便追溯。
- **安全性**: 用户输入的敏感信息（如 API Key）不得发送给 AI 模型（除非用于配置 AI 服务本身）。
- **强感知交互**: 所有 AI 操作必须提供可视化反馈（如 Loading 状态、思考过程、结果高亮），禁止无反馈的后台静默处理。

## Out of Scope

- **完全自动驾驶**: 系统不会在未经用户确认的情况下自动删除或大幅修改现有知识结构（必须有人类确认环节）。
- **多模态生成**: 本次重构仅关注文本内容的理解与结构生成，不涉及图片/视频的生成。
- **实时协作**: 不涉及多人同时编辑同一金字塔的冲突解决（沿用现有锁机制）。

## Assumptions

- **AI 能力**: 假设接入的 AI 模型（如 DeepSeek-V3/R1 或其他 LLM）具备足够的指令遵循能力和上下文理解能力。
- **数据迁移**: 现有的数据结构（Pyramid, Node, Content）需要扩展字段以存储 AI 分析结果，假设可以通过 Alembic 迁移完成。
- **前端重构**: 前端需要配合后端 API 的变化，增加"建议-确认"的 UI 组件。
