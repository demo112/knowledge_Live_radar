# AI-First 核心原则

## 一、原则定义

### 1.1 AI-First 定义
**凡是涉及"信息加工"的操作都必须经过 AI 处理。**

AI 不再是系统的"可选插件"或"辅助工具"，而是系统的"核心认知引擎"。
- 用户的所有输入（文本、URL、文件）首先进入 AI 层理解，再进入数据层存储。
- 用户的所有查询首先进入 AI 层解析意图，再进入索引层检索。
- 系统内部的所有状态变更（如抓取、更新）都触发 AI 层评估影响。

### 1.2 人机协作模式
系统遵循 **"AI 提议，人类决策"** 的协作模式：

```
用户输入 → AI 理解并生成建议 → 用户确认/修改 → 系统执行
```

**禁止模式**：
```
用户输入 → 直接保存 → 后台异步处理（用户看不到）
```

**协作要点**：
- **即时反馈**：用户必须在操作后立即看到 AI 的理解结果（<5秒）。
- **可修正性**：用户必须拥有修正 AI 理解和建议的权利。
- **透明性**：AI 的推理过程、置信度必须对用户可见。

---

## 二、信息加工场景识别

在设计新功能或审查现有功能时，使用以下清单识别是否需要 AI 参与：

1.  **理解类**：操作是否涉及理解用户输入的语义？（如搜索、分类、打标）
2.  **提取类**：操作是否需要从非结构化文本中提取结构化信息？（如从网页提取元数据）
3.  **生成类**：操作是否需要生成建议、摘要或结构？（如生成金字塔结构）
4.  **评估类**：操作的结果是否会影响知识结构的一致性？（如修改节点描述）

**判定规则**：如果任何一个问题的答案是"是"，则该操作**必须**经过 AI 处理。

---

## 三、设计检查清单

在进行技术设计和代码审查时，必须检查以下项目：

### 3.1 交互设计检查
- [ ] 用户输入后是否立即触发了 AI 分析？
- [ ] 界面是否清晰展示了 AI 的建议？
- [ ] 用户是否有明确的"确认"或"修改"入口？
- [ ] 是否提供了 AI 服务不可用时的降级方案？

### 3.2 架构设计检查
- [ ] 业务 Service 是否依赖了 `AI Core`？
- [ ] 数据流向是否遵循 `Input -> AI -> DB` 的顺序？
- [ ] 数据模型是否包含了 AI 元数据字段（如 `ai_reasoning`, `confidence`）？

### 3.3 API 设计检查
- [ ] 是否采用了两阶段 API 设计（Suggest + Confirm）？
- [ ] 响应中是否包含了 AI 分析结果？

---

## 四、例外情况

以下场景可以不经过 AI 处理：
1.  **纯管理操作**：如修改系统配置、用户权限管理。
2.  **精确查询**：如通过 ID 获取详情。
3.  **原始数据存储**：如存储抓取的 HTML 源码（但在处理时必须经过 AI）。

对于所有例外情况，必须在设计文档中明确说明理由。
